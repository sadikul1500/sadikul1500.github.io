Structural Design Pattern

Proxy Pattern

The Proxy Pattern is about controlling access by placing a middleman in front of the real object while keeping the same interface.

Definition

  • Proxy is entirely about controlling access.
  • A debit or credit card is a real-world proxy for actual money.
  • The proxy stands between the client and the real object.
  • It shares the exact same interface so the client feels like it is talking directly to the real object.

Problematic Scenario

Imagine a corporate application with a salary database. Without a proxy, any caller can directly access sensitive salary data, even if the user should not be allowed to see it.

C# No access control in front of the real database 
public class SecretDatabase
{
    public void DisplaySalaries()
    {
        // PROBLEM: There is no security! Anyone who calls this gets the data.
        Console.WriteLine("CEO Salary: $1M | Intern Salary: $20K");
    }
}

public class CorporateApp
{
    public void RunApp()
    {
        string myRole = "Intern";
        SecretDatabase db = new SecretDatabase();

        db.DisplaySalaries();
    }
}

Why the Bad Fix Is Still Bad

A quick fix would be putting role checks directly inside SecretDatabase. But that violates the single responsibility principle. The database should focus on fetching data, not acting like a security guard that manages roles and permissions.

When to Apply Proxy

  • Protection Proxy: check security before letting the client reach the real object.
  • Virtual Proxy: delay loading a heavy object until it is actually needed.
  • Remote Proxy: hide network communication for objects living on another server.
  • Caching Proxy: save expensive results and return them quickly on repeated requests.

Core Idea

The pattern says: create a middleman class, the proxy, that shares the exact same interface as the real object. The client thinks it is talking to the real database, but it is actually speaking to the proxy first. The proxy decides whether and when the real object should be accessed.

Proxy Pattern Solution

Introduce a proxy database that implements the same database interface, stores the user role, checks permission, and only forwards the request to the real database if access is allowed.

Pseudocode Proxy-based design 
IDatabase: DisplaySalary()

SecretDatabase: IDatabase
{
    DisplaySalary()
    {
        print("CEO: $1M, Intern: $20K");
    }
}

ProxyDatabase: IDatabase
{
    string userRole;
    IDatabase db;

    ProxyDatabase(ur) => userRole = ur;

    DisplaySalary()
    {
        if (userRole == 'Manager')
        {
            if (db == null) db = new SecretDatabase();
            db.DisplaySalary();
        }
        else
        {
            print("ACCESS DENIED");
        }
    }
}

main()
{
    userRole = 'intern';

    IDatabase myDb = new ProxyDatabase(userRole);
    myDb.DisplaySalary();
}

Key Idea

The client and the real object never need to know about the access-control details. The proxy handles those concerns and only delegates to the real object when the rules are satisfied.

Benefits

  • Keeps control logic separate from the real object.
  • Supports access control, lazy loading, remoting, and caching without changing client code.
  • Preserves the same interface for both proxy and real object.
  • Protects sensitive or expensive resources behind one controlled entry point.
