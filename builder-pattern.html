Creational Design Pattern

Builder Pattern

The Builder Pattern creates complex objects step by step and separates construction logic from the final product representation.

Definition

  • Builder is a creational design pattern that lets you construct complex objects step by step.
  • It extracts construction code from the product class and moves it into a separate builder object.
  • It is especially useful when the same construction process can produce different representations.
  • A Director can coordinate the steps in a fixed order to create standard configurations.

Main Idea

A complex object often needs many properties, options, and configuration steps. If all of that logic stays inside the product class, construction becomes hard to read and easy to misuse. Builder separates the "how to build" logic from the "what gets built" result.

Problem with Normal Code

A large constructor with many parameters is difficult to read and easy to misuse. The caller must remember what every argument means and pass values even for optional features.

C# Telescoping constructor problem 
public class Car
{
    // A massive list of properties
    public string Engine;
    public int Seats;
    public bool HasGPS;
    public bool HasTripComputer;
    public string PaintColor;

    // THE PROBLEM: The Telescoping Constructor
    public Car(string engine, int seats, bool hasGps, bool hasTripComputer, string paintColor)
    {
        Engine = engine;
        Seats = seats;
        HasGPS = hasGps;
        HasTripComputer = hasTripComputer;
        PaintColor = paintColor;
    }
}

public class App
{
    public void OrderCars()
    {
        // We want a simple sports car, but we are forced to pass confusing values
        // for things we don't care about. What does "true, false" mean here?
        Car sportsCar = new Car("V8", 2, true, false, "Red");

        // We want a cheap city car. We still have to pass feature flags manually.
        Car cheapCar = new Car("V4", 4, false, false, "White");
    }
}

Why This Is a Problem

  • Constructors become long and hard to understand.
  • Calling code is less readable because raw values hide their meaning.
  • Optional configuration makes constructor signatures grow quickly.
  • Construction logic remains trapped inside the product class.

Builder Pattern Solution

Move construction steps into a dedicated builder interface and let concrete builders create different results. One builder may produce a Car, while another builds a Manual using the same sequence of steps. A Director can run those steps in a predefined order for common configurations.

Pseudocode Builder-based design 
Car: engine: str, seat: int, hasGPS: bool, ShowSpec(): void
Manual: document: string

ICarBuilder: Reset(), SetEngine(), SetSeat(), HasGPS()
SuvCarBuilder, ManualBuilder: ICarBuilder
// GetResult(): Car, GetResult(): Manual

Director
{
    ICarBuilder _b;

    Director(ICarBuilder b): _b = b;

    BuildCarTypeA();
    BuildCarTypeB();
}

main class
{
    SuvCarBuilder b = new SuvCarBuilder();
    Director d = new(b);
    d.BuildCarTypeA();
    Car typeA = b.GetResult();

    ManualBuilder b1 = new ManualBuilder();
    d = new(b1);
    d.BuildCarTypeA();
    Manual m = b1.GetResult();
}

Role of the Director

The Director is optional, but it is very helpful when the application needs standard build recipes. Its job is to call building steps in a specific order, such as creating a standard SUV, a sports car, or a documentation manual using the same process.

Key Idea

Builder separates object construction from the final representation. The same sequence of steps can produce different outputs, and the client no longer needs to manage a long, fragile constructor call.

Benefits

  • Makes object creation easier to read and maintain.
  • Removes complex construction logic from the product class.
  • Supports step-by-step creation with clearer intent.
  • Allows the same build process to create different representations.
  • Provides reusable standard configurations through the Director.
