Structural Design Pattern

Facade Pattern

The Facade Pattern is about hiding complexity by placing one clean front-facing class in front of a large, messy subsystem.

Definition

  • Facade is entirely about hiding complexity.
  • It provides one simple interface in front of a complex subsystem.
  • The client talks to the facade instead of coordinating many subsystem classes directly.
  • The underlying subsystem still exists, but the facade makes common workflows easier to use.

Problematic Scenario

Imagine a smart-home movie setup. Starting movie night means coordinating a television, sound system, lights, and popcorn maker. Without a facade, the client must remember and manually execute every step in the right order.

C# Client manually coordinating the whole subsystem 
// 1. The Complex Subsystem Classes
public class TV
{
    public void TurnOn() { }
    public void SetInput(string input) { }
}

public class SoundSystem
{
    public void TurnOn() { }
    public void SetVolume(int level) { }
}

public class Lights
{
    public void Dim(int percentage) { }
}

public class PopcornMaker
{
    public void TurnOn() { }
    public void StartPopping() { }
}

// 2. The Client
public class SmartHomeApp
{
    public void StartMovieNight()
    {
        // PROBLEM: The client has to coordinate EVERYTHING manually.
        // If they want to watch a movie tomorrow, they have to write all this again.
        TV tv = new TV();
        SoundSystem sound = new SoundSystem();
        Lights lights = new Lights();
        PopcornMaker popcorn = new PopcornMaker();

        popcorn.TurnOn();
        popcorn.StartPopping();
        lights.Dim(20);
        tv.TurnOn();
        tv.SetInput("HDMI 1");
        sound.TurnOn();
        sound.SetVolume(11);
    }
}

When to Apply Facade

  • Client code is talking to many classes just to perform one logical action.
  • A new developer faces a high learning curve because one workflow depends on many subsystem classes.
  • We want to provide a simple default interface to a large messy legacy system without rewriting it.

Core Idea

The pattern says: create a single waiter-like class, the facade. That facade becomes the front-facing interface while the real subsystem remains behind it. The client gets a clean method such as StartShow() instead of manually orchestrating everything.

Facade Pattern Solution

Build a HomeTheaterFacade that owns the subsystem objects and coordinates them in the correct order. The client then performs the whole movie-night workflow with one or two method calls.

Pseudocode Facade-based design 
// Facade
class HomeTheaterFacade
{
    TV tv;
    SoundSystem soundSystem;
    Lights lights;
    PopcornMaker popcornMaker;

    Constructor(tv, soundSystem, lights, popcornMaker) => this.{x} = {x};

    StartShow()
    {
        tv.turnOn();
        lights.dim(30);
        soundSystem.setVolume(20);
        popcornMaker.getPopCorn();
    }

    EndShow()
    {
        popcornMaker.turnOff();
        lights.turnOff();
        soundSystem.turnOff();
        tv.turnOff();
    }
}

// Client
main()
{
    var homeTheaterFacade = new HomeTheaterFacade(
        new TV(),
        new SoundSystem(),
        new Lights(),
        new PopcornMaker()
    );

    // The client enjoys a perfectly clean, two-line execution!
    homeTheaterFacade.StartShow();

    // ... later ...
    homeTheaterFacade.EndShow();
}

Key Idea

Facade does not remove the subsystem. It simply gives the client a simpler doorway into it. The complexity stays hidden behind one service that knows how to coordinate the pieces in a sensible default sequence.

Benefits

  • Reduces tight coupling between client code and many subsystem classes.
  • Lowers the learning curve for common workflows.
  • Provides a clean front-facing API over a messy legacy system.
  • Keeps orchestration logic in one place instead of repeating it in clients.
