Behavioral Design Pattern

Chain of Responsibility

Chain of Responsibility is about passing a request along a linked sequence of handlers until the right object decides to process it.

Definition

  • Behavioral patterns are about how objects communicate and assign responsibilities.
  • Chain of Responsibility passes a request through a chain of handler objects.
  • Each handler checks whether it can process the request.
  • If it cannot, it forwards the request to the next handler in the chain.

Problematic Scenario

Imagine an expense approval system. Small expenses can be approved by a manager, medium ones by a director, and larger ones by the CEO. Without a pattern, the logic often becomes one rigid block of conditionals.

C# Monolithic approval logic 
public class ExpenseReport
{
    public string Purpose;
    public double Amount;
}

public class ExpenseHandler
{
    public void ProcessExpense(ExpenseReport expense)
    {
        // PROBLEM: A massive, rigid if/else block!
        if (expense.Amount <= 1000)
        {
            Console.WriteLine($"Manager approved ${expense.Amount} for {expense.Purpose}");
        }
        else if (expense.Amount <= 5000)
        {
            Console.WriteLine($"Director approved ${expense.Amount} for {expense.Purpose}");
        }
        else if (expense.Amount <= 10000)
        {
            Console.WriteLine($"CEO approved ${expense.Amount} for {expense.Purpose}");
        }
        else
        {
            Console.WriteLine($"Expense of ${expense.Amount} requires a Board Meeting!");
        }
    }
}

When to Apply Chain of Responsibility

  • Code is a giant switch statement or a wall of if/else checks to decide who should handle a request.
  • We want to decouple the sender of a request from the receiver.
  • We need to change the order of handlers dynamically at runtime.

Core Idea

The pattern says: take every branch of the conditional logic and turn it into its own standalone handler class. Then link those handlers together with a Next reference. Each handler asks one question: can I handle this request? If not, it passes the request forward.

Chain of Responsibility Solution

Each approver becomes one object in the chain. The manager checks first, then the director, then the CEO. The client only sends the request to the start of the chain and does not need to know who eventually handles it.

Pseudocode Chain-based design 
abstract class Approver
{
    Approver nextApprover;

    SetNext(Approver a) => nextApprover = a;

    abstract ProcessRequest(ExpenseReport r);
}

Manager: Approver
{
    ProcessRequest(ExpenseReport r)
    {
        if (r.amount <= 5000) => approve;
        else if (nextApprover != null) => nextApprover.ProcessRequest(r);
    }
}

Director: Approver
{
    ProcessRequest(ExpenseReport r)
    {
        if (r.amount <= 15000) => approve;
        else if (nextApprover != null) => nextApprover.ProcessRequest(r);
    }
}

CEO: Approver
{
    ProcessRequest(ExpenseReport r)
    {
        if (r.amount <= 50000) => approve;
        else => decline;
    }
}

main()
{
    var m = new Manager();
    var d = new Director();
    var c = new CEO();

    m.SetNext(d);
    d.SetNext(c);

    m.ProcessRequest(new ExpenseReport { Amount = 30000 });
}

Key Idea

The sender no longer decides who should handle the request. It simply sends the request to the first handler. Responsibility flows forward through the chain until one handler takes ownership.

Benefits

  • Removes large conditional blocks from the client.
  • Decouples the sender from specific receivers.
  • Makes approval or processing order easy to rearrange.
  • Keeps each handler focused on one responsibility.
