Structural Design Pattern

Adapter Pattern

The Adapter Pattern acts as a translator between incompatible interfaces so existing code can work with new or third-party systems without a risky rewrite.

Definition

  • Adapter allows two incompatible classes to work together.
  • It wraps an existing object and translates one interface into another.
  • It is also often called a Wrapper because it surrounds an existing service with a compatible API.
  • Its purpose is integration, not rewriting.

Problematic Scenario

Imagine a stock market application where the legacy system provides stock data in XML, but a newly purchased third-party analytics library accepts only JSON. The old system works, the new library is powerful, but the two interfaces do not match.

C# XML producer vs JSON-only analytics library 
// Our Legacy System (Works with XML)
public class StockDataProvider
{
    public string GetStockData()
    {
        return "<Stock><Ticker>AAPL</Ticker><Price>150</Price></Stock>";
    }
}

// The 3rd-Party Library (Works ONLY with JSON)
// We CANNOT edit this class
public class AdvancedAnalyticsLibrary
{
    public void AnalyzeData(string jsonData)
    {
        // THE PROBLEM: If we pass XML here, the library crashes!
        Console.WriteLine($"Drawing beautiful charts using JSON: {jsonData}");
    }
}

Why Direct Integration Fails

We have two bad choices. Rewriting the entire legacy system to emit JSON would be a large and risky refactor. Modifying the third-party library to accept XML is impossible because we do not own its source code. What we really need is a translator between the two systems.

When to Apply Adapter

  • You want to use an existing class, but its interface does not match the one you need.
  • You need to integrate a third-party library or legacy code without rewriting the whole application.
  • You need a translator between two incompatible systems.

Adapter Pattern Solution

Introduce an adapter that exposes the interface the application expects, accepts XML from the legacy system, converts that XML into JSON, and then forwards the translated data to the JSON-only analytics library.

Pseudocode Adapter-based design 
IAnalytics: Analyze(xmlData)

XMLToJSONAdapter: IAnalytics
{
    public readonly JSONAnalyzer;

    constructor(JSONAnalyzer _j_a)
    {
        JSONAnalyzer = _j_a;
    }

    Analyze(xmlData)
    {
        json = ConvertToJSON(xmlData);
        JSONAnalyzer.Analyze(json);
    }

    ConvertToJSON(xmlData)
    {
        returns json format data;
    }
}

main()
{
    // application produces xml data
    xml = GetData();

    var thirdPartyAnalyzer = new JSONAnalyzer();
    IAnalytics a = new XMLToJSONAdapter(thirdPartyAnalyzer);
    a.Analyze(xml);
}

Key Idea

The legacy code and the third-party library remain unchanged. The adapter stands between them and performs the translation. This preserves stable code, reduces risk, and keeps the integration logic isolated in one place.

Benefits

  • Lets incompatible interfaces work together.
  • Protects the application from large rewrites.
  • Keeps third-party and legacy code untouched.
  • Centralizes translation logic in one maintainable layer.
