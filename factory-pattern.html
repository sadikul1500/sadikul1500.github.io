Creational Design Pattern

Factory Pattern

The Factory Pattern creates objects through an abstraction so client code does not depend directly on concrete classes.

Definition

  • Create objects without tightly coupling the client to concrete classes.
  • Move object creation away from the client so the client is not responsible for calling new.
  • It belongs to the creational family of design patterns.
  • Objects are created through a superclass contract, while subclasses decide the concrete object to return.

Why It Is Needed

In traditional code, the client often creates concrete objects directly. That works at the beginning, but it introduces tight coupling. As soon as the application needs to support new delivery methods, the client class becomes full of conditionals, configuration branches, and concrete type knowledge.

Traditional Tight Coupling

Here the application depends directly on Truck. The client knows what to create and how to use it.

C# Tightly coupled client code 
public class Truck
{
    public void Deliver()
    {
        Console.WriteLine("Delivering cargo by land in a box.");
    }
}

public class LogisticsApplication
{
    public void PlanDelivery()
    {
        // TIGHT COUPLING
        Truck myTransport = new Truck();
        myTransport.Deliver();
    }
}

When the Business Expands

Supporting multiple delivery modes forces the client to decide which concrete class to instantiate. The result is growing complexity and repeated creation logic.

C# Conditional object creation in the client 
public void PlanDelivery(string mode)
{
    if (mode == "Road")
    {
        Truck myTransport = new Truck();
        // Truck configuration here
        myTransport.Deliver();
    }
    else if (mode == "Sea")
    {
        Ship myTransport = new Ship();
        // Ship configuration here
        myTransport.Deliver();
    }
}

Core Problem

  • The client is tightly coupled to Truck and Ship.
  • Every new transport type requires editing client logic.
  • Object creation and business flow are mixed together.
  • The code violates the open/closed principle because extending behavior often means modifying the client.

Factory Pattern Solution

Introduce a creator abstraction that defines a factory method. The base service knows how to run the shipment workflow, but subclasses decide which transport object should be created. This keeps business flow stable while allowing concrete products to vary.

Pseudocode Factory-based design 
ITransport: Deliver()
Ship, Truck: ITransport

abstract class LogisticService
{
    abstract ITransport CreateTransport();

    Shipment()
    {
        ITransport t = CreateTransport();
        t.deliver();
    }
}

RoadLogisticService, SeaLogisticService: LogisticService
// return new Truck() / Ship()

main()
{
    string mode;
    LogisticService l;

    if (mode == 'road') l = new RoadLogisticService();
    if (mode == 'sea') l = new SeaLogisticService();

    l.Shipment();
}

Key Idea

The client selects the appropriate creator once. After that, the creator controls which product gets instantiated. This removes repeated concrete object creation from the business workflow and keeps the code easier to extend.

Benefits

  • Reduces direct dependency on concrete classes.
  • Makes the code easier to extend with new transport types.
  • Separates creation logic from usage logic.
  • Keeps the client focused on behavior rather than construction details.
