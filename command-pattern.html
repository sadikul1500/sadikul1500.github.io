Behavioral Design Pattern

Command Pattern

The Command Pattern turns a request into a standalone object so actions can be stored, reassigned, executed later, and undone.

Definition

  • Command is about taking a request and turning it into a standalone object.
  • Chain of Responsibility passes a request down a line until someone handles it.
  • Command packages the request itself so it can be assigned, executed, stored, or undone.
  • This lets the sender trigger behavior without hardcoding the receiver's method directly.

Problematic Scenario

Imagine a video game with a player and an input handler. Button A jumps and Button B attacks. At first this seems fine, but the actions are physically hardcoded into the button methods.

C# Hardcoded controller actions 
public class Player
{
    public void Jump()
    {
        Console.WriteLine("Player jumped!");
    }

    public void Attack()
    {
        Console.WriteLine("Player swung sword!");
    }
}

public class InputHandler
{
    private Player _player;

    public InputHandler(Player player)
    {
        _player = player;
    }

    // THE PROBLEM: Hardcoded actions!
    public void PressButtonA()
    {
        _player.Jump();
    }

    public void PressButtonB()
    {
        _player.Attack();
    }
}

Why This Is a Problem

If the user opens settings and says, "Button A should attack, and Button B should jump," the current code is stuck. PressButtonA() physically calls _player.Jump(), so changing controls means changing the input handler code itself.

When to Apply Command

  • We need to reassign actions dynamically, such as remapping game controls.
  • We want to store executed actions so they can be undone later.
  • We want the caller to trigger behavior without knowing the exact receiver method.
  • We need to queue, log, schedule, or replay actions as objects.

Command Pattern Solution

Create one command interface with Execute() and Undo(). Each concrete command stores the receiver it needs, such as the player, and knows how to perform one action. The input handler stores commands instead of hardcoded player method calls.

Pseudocode Command-based input handling 
Player:
    Jump()
    Attack()

ICommand:
    Execute()
    Undo()

JumpCommand: ICommand
{
    Player player;

    JumpCommand(Player player) => this.player = player;

    Execute() => player.Jump();
    Undo() => writeline('reversing jump');
}

AttackCommand: ICommand
{
    Player player;

    AttackCommand(Player player) => this.player = player;

    Execute() => player.Attack();
    Undo() => writeline('reversing attack');
}

InputHandler
{
    ICommand ButtonA;
    ICommand ButtonB;

    Stack<ICommand> _commandHistory;

    PressButtonA()
    {
        ButtonA.Execute();
        _commandHistory.push(ButtonA);
    }

    PressButtonB()
    {
        ButtonB.Execute();
        _commandHistory.push(ButtonB);
    }

    PressUndo()
    {
        lastCommand = _commandHistory.pop();
        lastCommand.Undo();
    }
}

Main
{
    Player player;
    InputHandler controller;

    controller.ButtonA = new JumpCommand(player);
    controller.ButtonB = new AttackCommand(player);

    // playing game
    controller.PressButtonA();
    controller.PressButtonB();

    // undo
    controller.PressUndo();

    // change settings
    controller.ButtonA = new AttackCommand(player);
    controller.ButtonB = new JumpCommand(player);

    // playing game
    controller.PressButtonA();
    controller.PressButtonB();
}

Key Idea

The input handler no longer knows what a button really does. It only knows that a button has a command and commands can execute. That small separation makes remapping, undo, and command history natural instead of awkward.

Tradeoff

Command can create class explosion. If a game has 50 different actions, it may need 50 small command classes. That cost is often acceptable when it buys remapping, undo, replay, logging, or queueing.

Benefits

  • Decouples the sender from the object that performs the action.
  • Supports runtime action remapping.
  • Makes undo possible through command history.
  • Allows commands to be queued, logged, delayed, or replayed.
